1. Contexto e objetivo
Esta atividade é uma competição entre equipes da turma. O objetivo é aplicar, de forma crítica e justificada, as etapas de pré-processamento estudadas ao longo da disciplina (balanceamento, tratamento de dados ausentes, dados redundantes e inconsistentes, conversão simbólico-numérica, transformação de atributos numéricos, redução de dimensionalidade, seleção de instâncias, eliminação de outliers, dentre outras) e comparar o desempenho de diferentes algoritmos de classificação em um problema real de detecção de intrusão em redes de computadores.
Mais do que alcançar a melhor posição no ranking, a competição avalia se a equipe sabe justificar tecnicamente cada decisão de pré-processamento tomada e, principalmente, se sabe evitar armadilhas metodológicas como o vazamento de dados (data leakage), tema recorrente em todas as etapas já estudadas nesta disciplina até o momento.
2. Base de dados: NSL-KDD
O NSL-KDD é uma base de dados de detecção de intrusão em redes, amplamente utilizada em pesquisa de Aprendizado de Máquina aplicado à segurança da informação.
2.1 Características gerais ○ 41 atributos descritivos + 1 atributo de classe (tipo de ataque) + 1 atributo de nível de dificuldade ○ Atributos categóricos: protocol_type, service e flag ○ Classes de ataque fortemente desbalanceadas
2.2 Como acessar a base Os arquivos estão disponibilizados em Página Inicial / Trabalho Prático/ 1. treino.csv: conjunto de treino, com o atributo de classe (class: normal ou anomaly); 2. teste_sem_rotulo.csv: conjunto de teste sem o atributo de classe, com uma coluna id que identifica cada instância; 3. modelo_de_submissao.csv: modelo do arquivo de entrega, com as colunas id e class_prevista.
3. Formato da competição
○ Todas as equipes devem usar os MESMOS arquivos descritos acima. Não é permitido reembaralhar ou criar um split próprio, para garantir comparação justa entre equipes

○ Métrica oficial do ranking: F1-score macro no conjunto de teste (não use apenas acurácia, as classes são muito desbalanceadas, e a acurácia pode mascarar um classificador que ignora as classes raras)
3.1 Entrega das previsões no conjunto de teste Para preservar a integridade da competição, os rótulos (gabarito) do conjunto de teste não serão divulgados às equipes. Deixarei os seguintes arquivos no CANVAS:
○ treino.csv: conjunto de treino, com o atributo de classe (class: normal ou anomaly); ○ teste_sem_rotulo.csv: conjunto de teste sem o atributo de classe, com uma coluna id que
identifica cada instância; ○ modelo_de_submissao.csv: modelo do arquivo de entrega, com as colunas id e class_prevista. Depois de definir o pipeline final (ajustado somente com o treino), cada equipe deve aplicá-lo ao arquivo teste_sem_rotulo.csv e entregar um único arquivo de previsões, seguindo as regras abaixo:
○ Nome do arquivo: submissao_<número_da_equipe>.csv, em formato CSV com cabeçalho e separador vírgula.
○ Colunas obrigatórias: id e class_prevista. A coluna class_prevista deve conter apenas os valores normal ou anomaly (em minúsculas).
○ O arquivo deve ter exatamente uma linha para cada id do arquivo teste_sem_rotulo.csv, sem ids ausentes, repetidos ou extras, e sem valores vazios. Não altere a ordem nem os valores da coluna id.
○ Envio: Você deve enviar o arquivo “submissao_<número_da_equipe>.csv” pelo CANVAS até 28/11.
○ As previsões devem ser reproduzíveis: o notebook entregue (item 5) deve gerar exatamente o arquivo de previsões enviado. Previsões que não possam ser reproduzidas pelo notebook serão desconsideradas.
Após a entrega, compararei as previsões de cada equipe com o gabarito, calcularei as métricas de recall, precisão e F1 por classe e divulgarei o ranking da turma. Como o desempenho no teste só será conhecido após a entrega, as equipes devem estimar o desempenho esperado e escolher o melhor modelo apenas por validação cruzada (ou split de validação) dentro do treino. Arquivos fora do formato exigido não serão avaliados.
